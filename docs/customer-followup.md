# 团队客户跟进

入口：市场情报 → 客户跟进（`#market-intelligence/follow-up`）。

## 日常使用

负责人登录后点击“上传更新”，选择 UTF-8 编码的 `.md` 或 `.markdown` 完整台账（最大 512 KB）。预览主档数量、按编号比较的变化及完整原文，确认后保存。每次上传是独立完整版本，不将历史文件叠加成新客户。缺少客户总览或日期时保留原文阅读，并提示核对；不会猜测客户状态、付款、发送或发运事实。

“进度总览”按选中版本的排序约定展示。优先级台账默认按联系优先级升序；旧邮件处理日期台账保留从近到远、未知置末、同日源表顺序。处理日只读取该版本明确字段，不用客户来信、建议日或上传日填补。旧建议仅在详情历史参考中保留。点击客户阅读该版本的完整历史。“完整原文”保留其他附表、联系方式与备注，也可以下载原 `.md`。

“历史版本”显示资料日期与实际保存时间。负责人可恢复旧版；恢复会新增一条版本，现有记录继续保留。同事打开、切回页面或每分钟自动核对一次可见的最新版本；历史阅读不自动跳回新版。

页面顶部的“更新日期”可直接选择已有台账的资料日期，显示那一版的进度总览、完整原文和下载文件。没有台账的日期不会出现；同日多版默认打开当天最后保存的版本，并提供“当日版本”选择。未注明资料日期的文件明确按北京时间上传日显示。切换日期只切换阅读内容，不恢复或改写团队当前版本；可用“返回最新版”回到当前台账。

## 团队权限

负责人在“共享成员”添加同事**实际用于网站登录的邮箱**。同事使用已有的、邮箱已验证的 Supabase 账号登录后可以查看和下载，不能上传、恢复或管理成员。添加成员不发送邀请邮件，也不自动创建账号。移除后后续服务请求立即拒绝；已由成员保存的文件无法收回。

服务端每次通过当前项目 Supabase `/auth/v1/user` 核对 Bearer token 和已验证邮箱，再核对负责人/受邀名单。不是所有登录用户都能访问。返回内容设为 `Cache-Control: no-store`；前端不向 localStorage、公开客户数据或静态资源写入台账。Markdown 以 React 文本渲染，不执行上传的 HTML、脚本或链接。

本功能不写开发信发送记录，不生成正式公开客户，不发信、不提交表单。

## 部署与备份

沿用 `neon-lion-knowledge-proxy`，设置 `FOLLOWUP_OWNER_EMAIL` 为负责人的已验证登录邮箱。`FOLLOWUP_DB_PATH` 在容器中固定为 `/data/followup.sqlite3`，由专用 `followup-data` Docker volume 持久保存；容器重建不丢版本。目录仅应用用户可访问，不经 nginx 静态目录提供。现有代理的其他文档任务仍沿用原 Supabase 存储。

上线顺序：先更新代理源码、Dockerfile、Compose 与负责人环境变量，执行 `docker compose up -d --build`，验证匿名请求被拒；再发布前端。不要把原始台账、数据库、服务器环境变量或私人种子导入文件提交到 GitHub。

备份可通过容器内 Python `sqlite3.Connection.backup` 创建一致性副本，再将副本保存到私有备份位置；应同时保留负责人配置。恢复时先停止该代理，将备份放回 volume 并保持 UID/GID 10001 的所有权，随后启动验证。不要对该部署使用 `docker compose down -v`，这会删除台账 volume。

验证：`pnpm test -- tests/customerFollowup.test.ts`；代理镜像内执行 `python -m unittest discover -s tests -p test_followup.py`，使用临时数据库与模拟身份，不连接生产账号或更改发送历史。

## 完整版本索引（2026-10-26）

概览、详情、历史时间线、任务、发送核验、冲突、国内与其他线索、全部章节和原文共用选中快照。每个非空Markdown块保留原始行范围与安全显示位置；详情关联该客户原始章节及有明确编号、唯一联系人/公司名称或唯一邮箱的引用行。表头缺少分隔符只在结构化索引修复并提示，源文件不变。

概览保留全部字段，显示最新进度、当前状态、两类消息时间、等待对象、最近处理内容／发送状态和待确认事项。历史状态不会覆盖当前字段。来源按钮跳到当前版本原文行。未知Markdown以安全文本显示；全部章节与完整源文本始终可访问。

原始UTF-8文件（含BOM、换行）作为SQLite BLOB与文本、SHA-256、数据集ID和版本号一起保存。下载前重新核对成员权限并校验原始字节SHA-256；另提供受相同成员权限保护的 `/follow-up/versions/{id}/download`。既有无BLOB的快照兼容按原存储文本导出，不改变历史。

相同hash的任一历史文件再次上传返回重复提示。同数据集同版本不同字节必须显式勾选追加修订；旧版本号上传只存历史，不切当前。恢复仍需负责人显式操作。解析失败的上传仅存原文历史（activate=false），不替换当前；失败版本查看仅显示本版原文，不套用旧版索引。

时间线沿用源事件ID，其余按客户和源行定位；同分钟的明确事件重复引用只保留一事件及多个来源，不以日期合并不同邮件。任务保持原状态，无完成证据不自动完成；提及附件仅显示源记录及“原件未随本次文件提供”。

回归：`pnpm exec vitest run tests/customerFollowup.test.ts tests/followupCompleteness.test.ts tests/followupDatePicker.test.ts`；代理 `python -m unittest discover -s tests -p test_followup.py -v`。真实客户原文及浏览器截图仅存私有工作目录，不提交公开仓库。

## 客户名称与项目显示

普通视图显示“客户公司／联系人 · 对应产品”，保留客户ID作为内部键。支持原编号台账，以及文件头customer_identity_map、project_display_overrides和customer_id/event_id/task_id注释。总览客户名称打开原档案；邮件、报价付款、样品、任务、冲突和原文渲染中的名称打开同版客户详情。冲突涉及两客户时各有入口，不合并建档。未归属后缀与未知字段照录；缺少明确项目时显示“对应产品待确认”。

项目覆盖只从源文件明确产品和映射读取；同一客户的其他项目共用客户ID。内部注释及版本映射在普通视图隐藏，在源文本/复制/原始字节下载中完整保留。名称显示调整不修改原始快照、事件键、任务键、权限或业务状态；新台账资料更新仍沿用追加快照机制。

## 最近邮件处理日期（r3字段）

主表第二列“最近邮件处理日期”映射为lastEmailProcessedDate，第十一列“最近处理内容／发送状态”映射为processingActionText。来信时间、已发时间、处理日期、历史建议与上传日期独立。仅明确的ISO日期可用于排序，未知、日期范围及“某日后”均保持null，不补时分。读旧版时未提供的处理字段明确待核，不由旧建议日推算。

处理来源同时关联主表和源文件“最近邮件处理日期依据”表，保留依据文本、行范围及日期精度；详情可跳同版原文行。拟稿、附件核查与确认发送按原文区分，不因有处理日自动标已发送。暂停仅作状态，不覆盖日期排序。

默认降序、未知置末，同日按源表行序；用户可选择升序或源文件行序。清除筛选／排序恢复默认。任务不从处理日生成排期；原SERICHIM任务状态逐项保留，不整组重置或完成。导入预览增加有日期／待核数量、明确事件及新增事件键统计。

回归增加`tests/followupProcessing.test.ts`，覆盖新12列、日期来源、降序、同日顺序、暂停及未知置末，并防止从客户来信、旧建议或一般内部资料工作推定处理日。

## 联系优先级与内嵌历史快照（2026-10-28）

`default_sort_field: contact_priority_rank` 的六列主表以“顺序”为明确优先级，左列同时显示优先级、理由、最近邮件处理日期及发送状态。可切换邮件处理日期或源文件顺序；清除筛选恢复本版本默认排序。带括号说明的明确处理日期保留说明；处理日期仍不等于实际发件日期。

客户ID读取主表单元格及档案标题附近的明确注释，不把标题序号当客户ID。支持缩进或无缩进的身份映射，以及国内咨询类别；未知公司、产品、联系方式仍照原文保留。当前字段从“截至…最新口径”表取得，来信、已发、内部处理与等待对象独立。

文件声明 `archive_scope: …historical_only` 且存在“完整历史快照（仅供溯源）”时，该章及后续旧快照保留全部原文、旧事件与任务，但不会覆盖当前执行档案、排序、日期依据或生成旧催款任务。历史来源明确标注，当前发送核验、国内记录和新增/纠正事件可直接查看；原事件/任务ID保留，不凭显示名另建档。国内记录包含其原表行、对应补充说明和已有历史。

回归增加 `tests/followupPriority.test.ts`，使用虚构记录验证标题序号与真实ID不同、两种身份映射格式、当前已付款与历史待付款隔离、国内微信/咨询及新增事件保留。真实台账、校验与截图仍只存私有目录。
